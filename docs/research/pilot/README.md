# 基线试验：不装 skill 时 Agent 的改动范围召回

调研阶段做的试验，目的有两个：确认三类漏召回问题在当前 Agent 上能不能复现；沉淀一套之后评测还能用的样例仓库和评分脚本。

一共跑了两轮，第一轮作废，第二轮有效。下文的结果和观察都来自第二轮。

- **第一轮（6 次，作废）**：通过 Workflow 工具启动。Workflow 会把触发它的用户消息和上一条助手消息原文转给每个子代理，那条助手消息里写着本项目的"分级处理"规则。子代理的推理记录显示，它们明确按"用户的分级策略"行事，所以结果不能代表默认行为。原始结果留在 `results/round1-void/`，只作对照。
- **第二轮（9 次，有效）**：改用 Agent 工具直接启动子代理。启动前用一个测试子代理确认过，这种方式不转发对话，也不带项目 memory。运行期间标准答案移出了项目目录，样例仓库副本放在 `/tmp/shop-xxxx` 这类看不出用途的路径下。事后检查了 9 次运行的全部工具调用：除了共用的 Playwright 浏览器（见"局限"），没有一次访问自己副本以外的路径，工具输出里也没有出现设计文档或标准答案的内容。

## 设置

| 项 | 内容 |
|---|---|
| 样例仓库 | `fixture/shopfront/`：TS 前后端 monorepo，40 个文件（React 前端、Express 后端、API 文档） |
| 执行者 | general-purpose 子代理，不装任何 skill。模型是 Opus 5.5（由用户设置 `CLAUDE_CODE_SUBAGENT_MODEL` 指定），effort 为 max，两项都从运行记录里核实过。子代理会加载用户的全局 CLAUDE.md |
| 次数 | 3 个任务各跑 3 次，每次在一份独立副本里运行，9 次并发 |
| 标准答案 | `gt.json`，每个位置标一个等级：direct 应直接改；coupled 是需求关联，应改或带证据提出；review 是边界情况，应提出；exclude 不该改 |
| 评分 | `grade.py` 对比副本和原始仓库，逐个位置判定：edited（改了）、mentioned（没改，但最终汇报里提到了）、missed（漏掉）。T2 要求新增的行里出现动画相关写法才算改了 |

任务 prompt 用的是用户口吻，没有任何"要找全"之类的提示：

- **T1**（场景 1，需求关联）：把注册表单的密码最小长度从 8 位改成 12 位。
- **T2**（场景 2，同类组件散落）：给项目里所有弹窗类组件加上打开时的淡入动画，时长 200ms。
- **T3**（场景 3，重复实现抽取）：项目里有不少重复的日期格式化逻辑，帮我统一抽取成公共工具函数，并替换掉所有重复的实现。

各任务埋的陷阱：

- **T1**：同一条密码规则还散在重置密码表单、后端校验、中英文文案、单测和 API 文档里，写法各不相同（常量、字面量 `>= 8`、"至少 8 位"）。API 文档写明重置密码"与注册规则相同"。
- **T2**：6 个弹层命名各异，其中两个名字里看不出是弹窗：结算页里内联的地址选择遮罩，和命令式创建 DOM 的优惠券层 `couponLayer.ts`。Drawer、Toast 是边界情况，Tooltip 不该改。
- **T3**：6 处重复实现，其中 3 处已经写偏：月份少了 +1、没有补零、按 UTC 取日期。`useCountdown.ts` 是干扰项。

## 观察

1. **"找不全"在这个小仓库里没有复现。** 9 次都覆盖了全部 direct 位置，包括两个名字里看不出是弹窗的位置。coupled 和 review 位置要么改了，要么带证据列了出来。不该改的位置一次也没误改。

2. **Agent 自己会用多种特征联合检索，读多少文件取决于任务。** 下表是从运行记录里提取的 grep 模式：

| 任务 | 检索用的特征 |
|---|---|
| T1 | 领域词的中英文和缩写（password、pwd、密码）；已知标识符（`MIN_PASSWORD_LENGTH`、`passwordHint`）；旧值和它的上下文（`\b8\b`、"至少…8"、"8 位"、"八"、eight） |
| T2 | 结构特征（`createPortal`、`position: fixed`、`z-index`）；弹层的各种叫法（modal、dialog、popover、overlay、mask、sheet、drawer、lightbox、scrim、backdrop）；中文词（弹、浮层、遮罩、对话框、抽屉） |
| T3 | API 特征（`getFullYear`、`getMonth`、`toISOString`、`toLocaleDateString`、`padStart`、`Intl.DateTimeFormat`）；已知函数名；常见日期库（dayjs、moment、date-fns） |

T1 只读了 16 到 17 个文件，靠检索就找全了，因为每处关联代码都带着"password"或"8"。T2 和 T3 除了检索，还成批读了 24 到 40 个文件，其中 T2-c2 读完了全部 40 个。

3. **能复现的问题出在场景 1 的范围决策上。** 3 次 T1 都找到了全部关联位置，但处理方式不一样：

| 运行 | 后端校验 | API 文档 | 重置密码表单 |
|---|---|---|---|
| T1-c1 | 列出，待确认 | 列出，待确认 | 列出，待确认 |
| T1-c2、T1-c3 | 改了：新增一个只给注册用的 12 位常量 | 改了：把"重置与注册规则相同"改成"重置至少 8 位" | 列出，待确认 |

后两次等于 Agent 自己决定把一条共用规则拆成两条，还删掉了文档里写明这条约束的那句话，事后才在汇报里问用户重置要不要也改。按已确定的分级处理，后端校验和 API 文档都属于"推断出的关联项"，应该先确认再改。

4. **T2、T3 的范围判断在 3 次之间一致。** T2 三次都把 Drawer 算作弹窗并改了，Toast 和 Tooltip 都没改，并在汇报里列出。T3 三次都给日报保留了 UTC 语义（新增 `fmtDateUTC`），都把"两个接口时区不一致"和"前后端各留一份"列为待决定，都修正了月份少 +1 和没补零这两处偏差，并说明了页面上能看到的变化。

5. **和第一轮对照，有一条附带线索。** 第一轮的 2 次 T1 在上下文里看到了分级规则，结果都只改注册表单，把 3 处关联项列为待确认；第二轮 3 次里只有 1 次这样做。这提示：把分级规则放进 Agent 的上下文，就能改变它的范围决策，这正是 skill 起作用的方式。不过样本只有 2 次对 3 次，两轮的启动方式也不同，只能算线索。

6. **T2 的成本最高。** T2 每次 13 到 20 分钟、约 11.6 万到 16.3 万 token，是 T1 的 2 到 3 倍。原因之一是三次都启动了 Playwright 浏览器去验证动画效果，其中一次还起了本地 HTTP 服务。

## 局限

- 仓库只有 40 个文件，Agent 能读完大部分，不代表真实项目的规模。
- 执行者用的是 Opus 5.5 加 max effort。换成主会话里实际干活的模型（这次是 Opus 4.8）、Sonnet、Haiku 或更低的 effort，结果可能不同。每个任务只跑了 3 次。
- 执行者是子代理，不是全新的 Claude Code 主会话。长对话、上下文压缩、先出 plan 再执行这些情况都没覆盖。原计划用 `claude -p` 跑独立会话，那条命令关闭了审批，被 auto mode 拦下了。
- 子代理加载了用户的全局 CLAUDE.md，其中"只解决被要求的问题""如实汇报"的约定会让 Agent 偏保守。子代理的环境信息里还有项目目录名 `change-propagation`，有一点暗示。
- 评分是启发式的。mentioned 只是按文件名或标识符匹配汇报文本，可能偏高；读到的文件数也是估算。
- 3 次 T2 共用当前会话的同一个 Playwright 浏览器，能看到彼此打开的页面。核对时间戳后确认，三次都是先改完代码才开始用浏览器，所以只可能影响动画验证，不影响改动范围。

## 对后续工作的启示

- **问题定义要加上条件。** 至少在"Opus 5.5 加小仓库"这个组合下，漏召回不是检索能力的问题。值得检验的条件有：仓库大到读不完，只能靠检索；关联关系不带共同的词或结构，比如同一规则的另一种写法、配置文件、另一个仓库；更弱的模型或更低的 effort；长会话后期，或先计划后执行。
- **场景 1 的重点是决策，不只是检索。** skill 要把找到的关联项和背后的约束（比如"重置与注册规则相同"）列出来，按分级规则先确认再改。没确认之前，尤其不能改写记录约束的文档。
- **检索策略可以借鉴 Agent 已有的做法**（见观察 2 的表）。skill 的价值在于让这种做法每次都发生、在大仓库里也做得完，再补上 grep 做不到的检索方式（git 共变历史、LSP 引用、重复代码检测），改完后再查一遍有没有残留。
- **评测要换成大仓库。** 可以把同类陷阱植入真实的大型开源仓库，也可以复用真实项目里发生过的漏召回案例。指标除了召回率和误改，还要看范围决策是否合规（关联项是否先确认、约束是否保留），以及成本。

## 复现

```bash
# 每次运行一份独立副本：$CP_RUN_ROOT/cp-run-<RUN_ID>/shopfront，可以是指向中性路径的符号链接
export CP_RUN_ROOT=/tmp/cp-grade
for r in T1-c1 T2-c1 T3-c1; do mkdir -p $CP_RUN_ROOT/cp-run-$r && cp -R fixture/shopfront $CP_RUN_ROOT/cp-run-$r/; done
# 让 Agent 在副本里完成任务，把各次最终汇报存成 {"T1-c1": "...", ...}，再评分；没有汇报就传 -
python3 grade.py . finals.json T1-c1 T2-c1 T3-c1
```

做盲测时，运行期间要把 `gt.json` 和本 README 移到 Agent 看不到的位置，也不要用 Workflow 启动执行者。
